# 双人盲标规划与答案回收设计（v3）

本文说明 `annotation-plan` / `annotation-resolve` 的数据模型、精确求解器、答案状态机、
争议补位与包自校验。仅使用 Python 标准库。v1 单次分析与 v2 修订账本链路保持不变，
本链路不写账本，交付物是可续用的自校验 JSON 标注包。数据契约见 [contract.md](contract.md)。

## 1. 数据模型与确定性

- 输入经 `validate_plan` 严格校验后，所有数组按稳定键排序（训练/pool 按 `id`、标注员
  按 `id`、配额按组名），因此源数组换序不改变最终包字节。
- 概率复用 v1 的 `isotonic.fit`（同一套加权 PAVA），再用 `bisect_right` 在块下界上做
  阶梯预测；概率与候选价值都保留为精确 `fractions.Fraction`，序列化时存规范分数字符串。
- 包内不含时间戳、随机数或环境相关字段；`package_sha256` 是对“去除自身 SHA 字段后的
  排序键紧凑 UTF-8 JSON”取 SHA256，外部可独立复算。

## 2. 精确分配问题

约束：每候选两个**不同且 eligible** 的标注员；每 entity 至多选一条；标注员处理同一
entity 至多一条（同 entity 候选同组，选其一即封锁该 entity）；每任务 1 预算 + 两点
capacity；每组覆盖在 `[min,max]`。目标字典序为
`(候选价值之和, 覆盖候选数, 排序后的 (id, 较小人员, 较大人员) 元组序列)`。

这是一个带容量与配额的组合优化。规模被契约硬限制：pool ≤ 18、标注员 ≤ 8、组 ≤ 4、
budget/capacity ≤ 36。实现采用下面的“方案 A”，并保留“方案 B”作为可替换的等价设计。

### 2.1 方案 A（已实现）：子集枚举 + 二分 b-匹配

把“选哪些候选”与“由哪两个人接单”解耦：

1. **子集搜索**：按 pool 的 id 顺序做 2 选 1（选/不选）DFS，维护剩余预算、每组覆盖
   `cov` 与已占用 entity 位掩码 `blocked`（int 位图，O(1) 判定）。叶节点只在组下界
   全部满足时可行。
2. **配对可行性**：对叶节点的具体候选子集，构造源→候选（容量 2）→合格标注员
   （容量 1）→汇（容量 = 该标注员剩余 capacity）的网络，用 Dinic 最大流判定能否让
   每个候选都获得两个不同标注员。节点至多 18 + 8 + 2，最大流是多项式时间。
3. **字典序最小配对**：可行配对不是任意取一个最大流，而是按候选 id 顺序，对每个候选
   枚举其合格标注员对（已按 id 排序），每固定一个最小可行 pair 就用一次最大流验证
   其余候选仍可完成，从而得到全局字典序最小的 `(id, 人员, 人员)` 序列。

- **固定任务表示**：补位时把已有任务作为 `initial_fixed` 传入，先在 `_residual_context`
  中一次性扣除其预算与两点 capacity；争议任务通过 `disputed_ids` 不计组覆盖、其 entity
  并入 `blocked`。残差搜索只在“未分配且未封锁”的候选上进行，天然不会挪人换样。
- **容量状态表示**：容量是 `{标注员: 剩余整数}` 的字典；最大流在汇边容量上直接消费它，
  不需要在子集 DFS 的状态里展开人员维度。
- **剪枝**：组下界可达性（后缀中未封锁候选数不足即回退）、预算/组上界/entity 位图快速
  失败。叶节点最大流本身也是强剪枝——大量结构上可行但无法排班的子集在此被拒。
- **资源代价**：子集树最坏 O(2^18) ≈ 26 万条路径，每叶一次小型最大流；实测 18 候选、
  8 标注员的稠密最坏结构约 5–9 秒（离线一次性规划），内存随子集树与小型网络线性增长。
  正确性由 `tests/test_annotation.py` 的小规模穷举 oracle 独立核对（60 个随机实例）。

### 2.2 方案 B（等价备选）：候选×人员对的联合记忆化 DFS

不做解耦，直接在每个候选上枚举“跳过”或“选某个合格人员对”：

- **状态与容量表示**：DFS 状态为 `(位置, 剩余预算, 各标注员剩余 capacity 元组,
  每组覆盖元组, 已封锁 entity 集合)`，用记忆化缓存相对 `(价值, 计数)` 最优。capacity
  用整数元组、entity 用位掩码以降低键开销。
- **固定任务**：同样先扣除固定足迹并把残差容量/残差配额作为 DFS 初值；字典序平局可在
  DFS 内用“同 (价值,计数) 取更小元组序列”的比较器一次完成，无需二次重建。
- **剪枝**：价值后缀上界、计数上界（剩余预算、总容量//2、组上界余量、未封锁 entity
  数的最小值）、组下界可达性，以及“产生相同残差容量向量的人员对去重”。
- **代价与放弃原因**：该设计在 pool 较小时更快（无最大流开销），但人员对分支
  （单候选至多 C(8,2)=28 个 pair）与 capacity 元组组合使记忆化状态在稠密实例上爆炸，
  最坏结构无法在可接受时间内收敛。方案 A 用多项式最大流吃掉人员维度的组合爆炸，
  在契约上限内更稳。两者目标函数与所有约束完全等价，可在不改包格式的前提下互换。

### 2.3 不可行与 best-effort

严格下界无解时，把残差组下界放松为 0（保留所有上界、预算、容量、entity 约束）再求一次
最优，得到仍可排班的最佳努力任务；包状态由最终 `gaps`（min − 实际覆盖）如实标记为
`infeasible`。放松只影响“选多少”，不伪造可行性，也不改变价值/计数/字典序口径。

## 3. 答案状态机与争议补位

- 整批答案先做**全部**校验（摘要、任务存在、人员在分配对中、无重复、无改写），通过后
  才落地，任何一条失败都不动旧包。
- 状态由答卷数量与标签一致性纯函数推导：0→`open`、1→`pending`、2 同标→`agreed`、
  2 异标→`disputed`；`verify_package` 会重算该状态，伪造状态无法通过自校验。
- 仅 `agreed` 行进入 `truth`，字段对齐 v1 训练行契约，可直接作为现有分析输入。
- 出现 `disputed` 才触发补位：争议任务保留两份预算/容量足迹但退出组覆盖并封锁 entity；
  其余任务（含 pending/agreed）的分配整体固定。补位搜索复用第 2 节求解器，目标只在补位
  候选上比较；旧任务与新任务合并后再次统一校验预算与 capacity。补位不可行不退款、不丢
  答案，输出带残余缺口的 infeasible 包，后续仍可继续回收。
- 概率与价值在 plan 时封定，resolve 不重训、不重算，保证多轮回包间排序依据恒定。

## 4. 自校验、原子发布与错误语义

- `verify_package` 在每次 plan/resolve 末尾及 resolve 入口运行：重算 SHA256、重放 PAVA
  与逐候选概率/价值、核对任务状态/答卷/人员资格、预算与容量用量、组覆盖、缺口、真值，
  以及“同 entity 不重复任务”等不变量。
- 发布复用 `common.save`：临时文件 + `os.replace` 原子替换，符号链接拒绝。resolve 允许
  输出与输入包同路径，因为所有读取与校验都在替换前完成。
- 输入或计算错误退出码 2 且保留旧输出；合法但 infeasible 退出码 0 并在包与 CLI 回执中
  显式标注，包仍可继续回收剩余任务。
